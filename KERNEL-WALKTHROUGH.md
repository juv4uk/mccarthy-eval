# mccarthy-kernel.s — пояснення коду, функція за функцією

Цей документ пояснює те, що ДОДАЛОСЬ у `mccarthy-kernel.s` порівняно з
`mccarthy-eval.s` — про спільний фундамент (`cons`/`car`/`cdr`/
`atomp`/`eq_prim`, `cadr`/`caddr`/`caar`/`cadar`/`caddar`, `assoc`,
`pair`/`append`/`evlis`, дисципліна callee-saved регістрів, вирівнювання
стека) читай `CODE-WALKTHROUGH.md` — там усе це вже пояснено докладно,
і в `mccarthy-kernel.s` воно не змінилось. Тут — лише те, чого вчора
не було: тег для чисел, reader, динамічна таблиця символів, нові
гілки `eval` (`ATOM`/`EQ`/`COND`/`LABEL`/арифметика), `appq`, printer,
`main`/REPL.

## 1. Тег для чисел (рядки 80-88)

```asm
/* bits[1:0] == 00  -> cons pointer (16-байтно вирівняна адреса купи)
 * bits[1:0] == 01  -> symbol   (payload = value >> 2)
 * bits[1:0] == 11  -> fixnum   (payload = value >> 2, арифметичний зсув) */
.equ NIL_SYM, 1
.equ T_SYM,   5
```

Учора був лише 1 біт (символ/вказівник). Сьогодні — 2 біти: `00`
лишається вказівником (клітинки купи все ще завжди кратні 16, тож їх
2 нижні біти фізично завжди нулі), `01` — символ, `11` — ціле число.
`atomp` (перевірка "чи це НЕ вказівник") не змінилась — вона й досі
просто дивиться на біт 0, і цей тест лишається правильним і для
символів, і для чисел одночасно.

**Важлива деталь**: формула тегування символів змінилась з `id*2|1`
на `id*4|1` (щоб біт 1 завжди лишався `0` для символів, звільняючи
його для розрізнення з числами). Через це `T_SYM` учора був `3`,
сьогодні — `5`. Кожен символ отримав новий числовий тег, але сама
СТРУКТУРА коду, що з ним працює, не змінилась.

## 2. Числові гелпери (рядки 121-141)

```asm
fixnump:                     /* fixnump(rdi=val) -> rax (1/0) */
    mov     %rdi, %rax
    and     $3, %rax
    cmp     $3, %rax
    sete    %al
    movzx   %al, %eax
    ret

mkfix:                       /* mkfix(rdi=n) -> rax = тегована фіксована крапка */
    mov     %rdi, %rax
    shl     $2, %rax
    or      $3, %rax
    ret

getfix:                      /* getfix(rdi=tagged) -> rax = справжнє ціле, зі знаком */
    mov     %rdi, %rax
    sar     $2, %rax
    ret
```

`fixnump` — маска нижніх двох бітів і порівняння з `11`. `mkfix` —
зсув числа на 2 біти вліво (звільняє місце для тегу) і `OR 3`.
`getfix` — зворотна операція, **арифметичний** зсув (`sar`, не `shr`)
— це навмисно, щоб від'ємні числа зберігали знак (перевірено живцем:
`(DIFFERENCE 3 10)` дає `-7`, не сміття).

## 3. Динамічна таблиця символів (рядки 700-785)

Учора символи були компільованими константами (`.equ QUOTE_SYM, 5`
напряму в коді). Сьогодні `intern(rdi=ім'я, null-terminated) -> rax`
шукає ім'я в `symtab` (масив вказівників на рядки), і якщо не
знаходить — копіює рядок у постійне сховище (`strheap`, ще один
bump-allocator, як `heap`, тільки для тексту, не для cons-клітинок),
додає новий запис і повертає новий тег.

**Чому це важливо**: `NIL`/`T`/`QUOTE`/... інтерновані ПЕРШИМИ, у
фіксованому порядку, у `main` — саме тому їхні числові теги
передбачувані й `.equ`-константи (`QUOTE_SYM = 9` і т.д.) правильні.
Якщо колись зміниш порядок інтернування в `main` — усі ці константи
розсинхронізуються, і нічого одразу не зламається видимо, просто
`eval` перестане розпізнавати `QUOTE` як `QUOTE`. Крихке місце,
варте знати.

## 4. Reader — текст у S-вираз (рядки 786-943)

```
skip_ws       — пропускає пробіли/таби/переноси рядків
read_atom     — збирає символи до пробілу/дужки в tokbuf,
                перевіряє looks_numeric, або inter'ить, або parse_int
looks_numeric — чи весь токен (після необов'язкового '-') складається
                лише з цифр
parse_int     — рядок цифр -> ціле число -> mkfix
read_sexpr    — якщо наступний символ '(' -> read_list, інакше read_atom
read_list     — рекурсивно читає елементи до ')', будує cons-ланцюжок
```

**Реальний баг тут** (знайдений тобою живцем у REPL): `looks_numeric`
спершу перевіряв лише ПЕРШИЙ символ токена. `"5.124"` починається з
цифри — проходив як "число", а `parse_int` не перевіряв символи, тупо
віднімав `'0'` з кожного, включно з `.` (ASCII 46), що дає
переповнення байта (254), яке множилось у накопичувач як "цифра".
`(PLUS 5.124 1266.156)` давав `13218280` — не помилку, а тихе сміття.
Виправлено: `looks_numeric` тепер сканує ВЕСЬ токен, приймає лише
чисто цифрові послідовності. `"5.124"` тепер падає в `intern` як
звичайний (незв'язаний) символ — `(PLUS 5.124 ...)` дає чесний `0`,
не сміття. Дробові числа й досі не підтримуються (свідомо — дивись
нижче, чому ми НЕ поспішаємо в `float`).

## 5. `appq` (рядки 333-364) — той самий, що в McCarthy 1960

```asm
appq:
    push    %r12
    mov     %rdi, %r12
    cmp     $NIL_SYM, %r12
    je      .appq_nil
    mov     %r12, %rdi
    call    car
    mov     %rax, %rdi
    mov     $NIL_SYM, %rsi
    call    cons                /* (car[m]) */
    mov     $QUOTE_SYM, %rdi
    mov     %rax, %rsi
    call    cons                /* (QUOTE car[m]) */
    ...
```

Буквально `appq[m] = [null[m] → NIL; T → cons[list[QUOTE;car[m]]; appq[cdr[m]]]]`
з первинного джерела (`mccarthy-1960-eval-apply-primary-source-2026-08-28.md`).
Знайдений через реальний segfault, не з пам'яті: `plain_call` (гілка
"звичайний виклик функції") брала вже ОБЧИСЛЕНІ аргументи й
повторно згодовувала їх у `eval` без лапок — а `eval`, побачивши
готове значення (наприклад список `(A)`) як "код", намагався
викликати `A` як функцію. `appq` цитує кожен аргумент перед повторним
`eval`, захищаючи його від повторного обчислення. Викликається лише
в одному місці — `.plain_call` (рядок 605).

## 6. Нові гілки `eval` (рядки 365-699)

**Самообчислення `T` і чисел** (рядки 376-398) — обидва додані ПІСЛЯ
того, як живі тести показали, що без цього `T` і числа мовчки
перетворюються на `NIL` (детально розказано в `README.md`, розділ
"Two real bugs" і "A second real design bug"). Патерн однаковий для
обох: перевір спеціальний тег, поверни значення як є, не йди в
`assoc`.

**`ATOM`/`EQ`** (рядки 415-456) — обчисли аргумент(и), застосуй
примітив (`atomp`/`eq_prim`), перетвори булевий результат `1/0` назад
у Lisp-значення `T`/`NIL`.

**`COND`** (рядки 458+) делегує в `evcon` (рядки 290-332) —
ітеративно (не рекурсивно всередині `eval`, а через окрему функцію)
перевіряє клаузи, обчислює перший `TEST`, що дав НЕ-`NIL`, повертає
обчислений `RESULT` цієї клаузи. Якщо жодна клауза не підійшла — наша
свідома спрощена поведінка: повернути `NIL` (в оригіналі 1960 року це
не визначено).

**`LABEL`** (усередині `.head_not_atom`, перевірка `caar[e]` проти
`LABEL_SYM` на рядку 631) — на
відміну від оригінальної формули McCarthy, яка каже
`cons[list[cadar[e];car[e]];a]` (список із двох елементів), наш код
свідомо використовує `cons[cadar[e];car[e]]` (dotted pair) — щоб
залишатись сумісним із власним `assoc`, який усюди очікує dotted-pair
записи (так само, як `pair` будує їх для `LAMBDA`). Це задокументоване,
свідоме відхилення від букви першоджерела заради внутрішньої
узгодженості, не недогляд.

**Арифметика** (`ZEROP`/`TIMES`/`DIFFERENCE`/`PLUS`) — не з семи
примітивів McCarthy взагалі, прибудовані так само, як це роблять усі
реальні Ліспи: звичайні додаткові гілки диспетчера, `getfix`
розтегування, реальна `imul`/`sub`/`add`, `mkfix` тегування назад.
Жодна з ATOM/EQ/COND/CAR/CDR/CONS/QUOTE/LABEL/LAMBDA гілок при цьому
не змінювалась.

## 8. `main`/REPL/`process_buffer` (рядки 1038-1203)

Найбільша структурна зміна: логіку "читай форму, перевір чи DEFINE,
обчисли, надрукуй" винесено з `main` в окрему функцію
`process_buffer` — тому що тепер є ДВА режими, які мусять поводитись
ІДЕНТИЧНО:

- **Файловий режим** (`argc >= 2`): `fopen`/`fread`/`fclose` файл у
  `filebuf`, встанови `input_ptr`, виклич `process_buffer` ОДИН раз
  на весь буфер.
- **REPL-режим** (`argc < 2`): друкуй `"> "`, `fgets` один рядок у
  `linebuf`, встанови `input_ptr`, виклич `process_buffer` для ЦЬОГО
  рядка, повтори. `Ctrl-D` (fgets повертає NULL) — вихід.

**`argc` зберігається в пам'яті** (`argc_saved`), не в регістрі —
свідомо, щоб не порушити парність `push`/вирівнювання стека (зайвий
`push %r15` зробив би непарну кількість pushes від входу в `main`,
зсунувши вирівнювання для КОЖНОГО виклику всередині `main`).

**Знайдений і виправлений баг вирівнювання** (до того, як він
устиг щось зламати цього разу, не після): обгортка `fflush_stdout`
навколо `call fflush` додавала ще один push адреси повернення,
зсуваючи вирівнювання для ВНУТРІШНЬОГО виклику `fflush` — та сама
проблема, що вчора була в `print_pair` із `printf`. Виправлено —
`fflush(NULL)` викликається напряму в `.repl_mode`, без обгортки.

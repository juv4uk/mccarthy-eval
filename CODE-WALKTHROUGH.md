# mccarthy-eval.s — пояснення коду, функція за функцією

Цей документ пояснює САМ АСЕМБЛЕРНИЙ КОД у `mccarthy-eval.s` — не
McCarthy-код, який він реалізує (той розібраний окремо в
`/home/agents/ecosystem/docs/correspondence/mccarthy-1960-eval-apply-walkthrough-2026-08-28.md`).
Читай обидва документи паралельно: лівий стовпець — M-expression з
1960 року, правий — як саме він перетворений на реальні x86_64
інструкції.

Нотація асемблера — GNU assembler, AT&T-синтаксис (`%rdi`, не `rdi`;
джерело зліва, призначення справа: `mov %rax, %rbx` означає
"скопіюй rax у rbx", у зворотному порядку до Intel-нотації).

## 1. Представлення даних (рядки 4-8, коментар на початку файлу)

Кожне значення Ліспу — одне 64-бітне слово з одним прапорцем у
найнижчому біті:

```
біт 0 == 1  →  це символ (immediate atom); саме значення = (payload << 1) | 1
біт 0 == 0  →  це вказівник на cons-клітинку (16 байт: car:8, cdr:8)
```

Чому це працює без плутанини: клітинки виділяються через bump-
allocator по 16 байт за раз, починаючи з вирівняної адреси (`heap`,
`.align 16`), тож будь-яка адреса клітинки завжди кратна 16 — її
найнижчий біт фізично завжди `0`. Символи ж завжди непарні (`| 1`).
Перевірка "це атом чи пара?" (`atomp`) — це буквально одна інструкція
`and $1, %rax`.

## 2. Таблиця символів (рядки 35-43)

```asm
.equ NIL_SYM,    1     /* id 0 */
.equ A_SYM,      3     /* id 1 */
.equ B_SYM,      5     /* id 2 */
.equ QUOTE_SYM,  7     /* id 3 */
.equ CONS_SYM,   9     /* id 4 */
.equ CAR_SYM,    11    /* id 5 */
.equ CDR_SYM,    13    /* id 6 */
.equ LAMBDA_SYM, 15    /* id 7 */
.equ X_SYM,      17    /* id 8 */
```

`.equ` — асемблерна константа (не пам'ять, просто ярлик для числа,
підставляється при компіляції). Кожне значення = `(id << 1) | 1`:
id 0 → 1, id 1 → 3, id 2 → 5... — саме так формула з §1 дає непарні
числа. Дев'ять символів — рівно стільки, скільки потрібно для двох
трасувань, не більше (нема `T`, нема `EQ`, нема `ATOM`, нема `COND`,
нема `LABEL` — вони не викликаються жодним із двох прикладів).

## 3. П'ять базових операцій (рядки 48-73)

```asm
cons:                            /* cons(rdi=car, rsi=cdr) -> rax */
    mov     heap_ptr(%rip), %rax
    mov     %rdi, (%rax)         /* [rax] = car */
    mov     %rsi, 8(%rax)        /* [rax+8] = cdr */
    lea     16(%rax), %rdx       /* rdx = rax + 16, наступна вільна клітинка */
    mov     %rdx, heap_ptr(%rip)
    ret
```

`heap_ptr` — "поточна вільна адреса" в bump-allocator-і. `cons`
записує `car`/`cdr` в поточну клітинку, зсуває вказівник на 16 байт
уперед, повертає СТАРУ адресу (де щойно записав). Немає garbage
collection — кожен виклик просто йде далі по купі; для двох
трасувань і 4096 клітинок цього досить із великим запасом.

```asm
car:                             /* car(rdi=ptr) -> rax */
    mov     (%rdi), %rax
    ret

cdr:                             /* cdr(rdi=ptr) -> rax */
    mov     8(%rdi), %rax
    ret

atomp:                           /* atomp(rdi=val) -> rax (1/0) */
    mov     %rdi, %rax
    and     $1, %rax
    ret

eq_prim:                         /* eq_prim(rdi=a, rsi=b) -> rax (1/0) */
    xor     %eax, %eax
    cmp     %rsi, %rdi
    sete    %al
    ret
```

`car`/`cdr` — просто читання за адресою (з offset 0 чи 8). `atomp` —
маска найнижчого біта. `eq_prim` — пряме порівняння двох 64-бітних
слів (правильно для символів; для двох різних вказівників на
структурно однакові, але не тотожні клітинки дало б `false` — так
само, як в оригіналі: `EQ` визначений лише для атомів, п. 2.2 статті
1960 року).

## 4. `cadr`/`caddr`/`caar`/`cadar`/`caddar` — композиції (рядки 78-109)

```asm
cadr:                            /* car(cdr(rdi)) */
    call    cdr
    mov     %rax, %rdi
    jmp     car
```

Тут `jmp car` замість `call car` + `ret` — хвостовий виклик (tail
call): результат `car` — це і є результат `cadr`, тож немає сенсу
повертатись у `cadr`, щоб одразу зробити `ret` — просто передай
керування напряму в `car`, і коли ВІН зробить `ret`, він поверне
керування прямо туди, звідки викликали `cadr` (адреса повернення на
стеку не змінювалась). Економить одну інструкцію й трохи стека,
поведінка ідентична неоптимізованому варіанту.

Решта (`caddr`, `caar`, `cadar`, `caddar`) — той самий прийом,
довший ланцюжок `car`/`cdr` перед фінальним `jmp`.

## 5. `assoc` — пошук у середовищі (рядки 114-129)

```asm
assoc:
.assoc_loop:
    cmp     $NIL_SYM, %rsi
    je      .assoc_nil
    mov     (%rsi), %rdx        /* pair = car(alist) */
    mov     (%rdx), %rcx        /* key  = car(pair)  */
    cmp     %rcx, %rdi
    je      .assoc_found
    mov     8(%rsi), %rsi       /* alist = cdr(alist) */
    jmp     .assoc_loop
```

Це `assoc[e;a]` з McCarthy — але написана як ЦИКЛ (`jmp` назад на
мітку), не рекурсія. Можна було зробити рекурсивно (`call assoc`
замість `jmp .assoc_loop`), і формально це точніше відповідало б
оригіналу — але `assoc` — хвостова рекурсія (останнє, що вона робить,
— викликає саму себе з новим `alist`), тож цикл семантично
ідентичний, просто без зайвих push/pop на стеку. Це єдине місце у
файлі, де я свідомо відступив від "один в один рекурсія" заради
простоти — усі інші рекурсивні функції (`pair`, `append`, `evlis`,
`eval`) написані як справжня рекурсія через `call`.

## 6. `pair`/`append`/`evlis` — справжня рекурсія (рядки 134-231)

Ці три функції мають однакову структуру, тож розберемо одну —
`append` — детально:

```asm
append:                          /* append(rdi=l1, rsi=l2) -> rax */
    push    %r12
    push    %r13
    mov     %rdi, %r12          /* r12 = l1 (цей кадр стека, свій) */
    mov     %rsi, %r13          /* r13 = l2 */
    cmp     $NIL_SYM, %r12
    je      .append_base
    mov     %r12, %rdi
    call    car
    push    %rax                /* збережи car(l1) на стеку -- переживе рекурсивний виклик */
    mov     %r12, %rdi
    call    cdr
    mov     %rax, %rdi
    mov     %r13, %rsi
    call    append               /* рекурсія: append(cdr(l1), l2) */
    mov     %rax, %rsi
    pop     %rdi                 /* дістань збережений car(l1) назад */
    call    cons
    jmp     .append_done
.append_base:
    mov     %r13, %rax
.append_done:
    pop     %r13
    pop     %r12
    ret
```

**Чому `push %r12; push %r13` на самому початку — не забаганка, а
необхідність.** `r12`-`r15` — це "callee-saved" регістри за угодою
x86_64 System V ABI: функція, що ЇХ використовує, зобов'язана
зберегти й відновити оригінальне значення перед поверненням. Це
означає: коли `append` кладе `l1`/`l2` в `r12`/`r13`, а потім сама
себе рекурсивно викликає (`call append`) — новий, вкладений виклик
`append` зробить СВОЇ власні `push %r12; push %r13` на початку,
перезапише їх своїми власними `l1`/`l2`, а перед своїм `ret`
відновить те, що там було ДО нього. Тобто зовнішній `append` після
повернення з рекурсивного виклику знову бачить свої власні,
незмінні `r12`/`r13` — так, ніби рекурсивний виклик їх взагалі не
торкався. Це і є те, що дозволяє писати рекурсію природно, без
ручного передавання "збережи це десь окремо" — регістр сам
"пам'ятає" значення свого кадру завдяки дисципліні push/pop на
кожному рівні виклику.

`pair` (зшиває два списки в alist пар) і `evlis` (обчислює кожен
елемент списку через рекурсивний виклик `eval`) — та сама схема: свої
`r12`/`r13`, push перед рекурсією, той самий трюк.

## 7. `eval` — головний диспетчер (рядки 236-341)

Структура один в один повторює `cond` з McCarthy: `atom[e]` → пошук у
середовищі; інакше — перевір `car[e]` на кожен із символів по черзі
(`cmp` + `jne` до наступної перевірки — це і є `[eq[...]→...;
eq[...]→...;...]` каскад). Три регістри `r12`/`r13`/`r14` тримають
`e`/`a`/`head` цього конкретного виклику `eval` — за тим самим
callee-saved принципом, що й вище, тож навіть коли `eval` рекурсивно
викликає сам себе (гілка `CONS`, гілка `LAMBDA`) — кожен вкладений
виклик має власну, незалежну копію.

Одна тонкість у гілці `CONS`:

```asm
.try_cons:
    ...
    mov     %r12, %rdi
    call    cadr
    mov     %rax, %rdi
    mov     %r13, %rsi
    call    eval                 /* result1 = eval[cadr[e];a] */
    push    %rax                 /* збережи result1 -- бо зараз викличемо eval ще раз */
    mov     %r12, %rdi
    call    caddr
    mov     %rax, %rdi
    mov     %r13, %rsi
    call    eval                 /* result2 = eval[caddr[e];a] */
    mov     %rax, %rsi
    pop     %rdi                 /* result1 назад із стека */
    call    cons                 /* cons(result1, result2) */
```

Тут потрібен саме `push`/`pop` (не регістр), бо `result1` мусить
пережити ще один виклик `eval` — а всередині цього виклику `eval`
сама використовує `r12`/`r13`/`r14` для власних потреб. Стек — єдине
місце, гарантовано вільне від чужого втручання під час виклику.

Гілка `LAMBDA` (наприкінці) — це `append[pair[cadar[e];
evlis[cdr[e];a]];a]`, побудована з тих самих цеглинок, у тому самому
порядку виконання, що й у M-expression.

## 8. `print_sym`/`print_pair` — вивід (рядки 346-380)

`print_sym` — тривіальне порівняння з двома відомими символами (`A`,
`B`), повертає ASCII-код у `%al`. `print_pair` викликає `printf` із
форматом `"(%c . %c)\n"` — єдине місце у файлі, де важливо СУВОРЕ
16-байтне вирівнювання стека перед викликом (`call printf`), бо
glibc's `printf` реально використовує SSE-інструкції, які падають на
невирівняному стеку. Саме тому там один `push %rbx` на початку і
акуратний баланс `push %rdx`/`pop %rdx` навколо — щоб рівно перед
`call printf` стек був вирівняний.

## 9. `main` — побудова обох виразів (рядки 386-475)

Жодної хитрості — послідовні виклики `cons`, що вручну складають ту
саму структуру, яку в реальному Ліспі побудував би reader, читаючи
текст `(CONS (QUOTE A) (QUOTE B))`. Це і є те, чого зараз бракує
(reader) — `main` тут ГРАЄ роль reader-а, руками, для рівно двох
конкретних виразів.

## Знайдений і виправлений баг (для повноти картини)

Перша збірка падала (`segmentation fault`) усередині `cons`, при
записі за адресою `0`. Причина: `heap_ptr` лежить у `.bss`, а `.bss`
ОС ініціалізує нулями — але я забув явно вказати, щоб `heap_ptr`
показував на початок `heap`, перш ніж перший `cons` спробує туди
писати. Виправлення — два рядки на самому початку `main`:

```asm
lea     heap(%rip), %rax
mov     %rax, heap_ptr(%rip)
```

Знайдено через `gdb` (`bt` показав крах саме у `cons`, `info
registers` показав `rax=0`) — не здогадкою, а прямим спостереженням.

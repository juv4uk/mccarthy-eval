# RECON-06 closeout (issue #28)

`./run.sh` — єдиний відтворюваний closeout gate для standalone
historical reconstruction (#7). Не залежить від CML #180.

## Що робить

1. Фіксує toolchain (gcc/binutils/qemu versions), стан `mccarthy-kernel.s`
   (git HEAD, blob SHA-256), і machine profile (CPU model, попереджає,
   якщо це не заявлений i5-6400).
2. Збирає `mccarthy-kernel.s`, фіксує SHA-256 бінарника.
3. Ганяє всі три корпуси: `tests/historical-core/` (#9),
   `tests/isa-baseline/` (#7 фізичне виконання, статично + QEMU
   Conroe), `tests/historical-facility-extensions/` (#27).
4. **Перезбирає й перезапускає все вдруге**, звіряє SHA-256 бінарника
   між двома незалежними білдами — не просто "один раз пройшло", а
   реальна перевірка детермінованості.
5. Документує відомі regression witnesses (два реальні історичні баги,
   зафіксовані в #9).

## Реальна знахідка: недетермінований білд (виправлено)

Перший запуск цього closeout **знайшов справжню недетермінованість**:
два незалежні `gcc -no-pie -O0 -o mccarthy-kernel mccarthy-kernel.s`
(той самий вхідний файл, та сама машина) давали **різні SHA-256**
бінарника. Діагностовано напряму (`cmp -l`, `xxd`): gcc вбудовує
випадкове ім'я власного тимчасового `.o`-файлу (напр. `ccnOUnt6.o` vs
`ccht2cpm.o`) у `.strtab` фінального бінарника через внутрішній symbol
table запис асемблера -- стандартна, добре відома нетермінованість
C-тулчейну (`mktemp`-подібне ім'я), не баг реконструкції й не
відмінність у самому машинному коді.

**Фікс**: додано `-s` (strip symbols при лінкуванні) до кожного
`gcc`-виклику в репо (`build.sh`, `build-kernel.sh`, усі три
`tests/*/run.sh`). Підтверджено: байти самого коду (`.text` тощо) не
змінюються, лише прибирається symbol table, якою ніхто в цьому репо
не користується (немає debugger-workflow, немає `-g`). Після фіксу --
byte-identical SHA-256 між незалежними білдами, підтверджено
`cmp`/`sha256sum`.

## Toolchain drift, зафіксований чесно

`build.sh`'s власний коментар (2026-08-28) фіксував "gcc (Ubuntu
13.3.0-6ubuntu2~24.04.1)" як empirically confirmed build environment.
Живий стан машини зараз (2026-09-22): **gcc 16.1.0**, GNU Binutils
2.44. Це не суперечність -- toolchain на машині оновився за час між
сесіями, і саме тому `run.sh` фіксує live-версії щоразу, а не покладається
на застарілий коментар в іншому файлі (пряма ілюстрація принципу "жива
машина > пам'ять/старий запис", яким керується вся ця реконструкція).

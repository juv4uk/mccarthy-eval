# Provenance: `GET`/`DEFLIST`/`REMPROP` -- property lists (issue #7)

## Джерело

**LISP 1.5 Programmer's Manual (1962)**, розділ "7.3 Property Lists"
(ст.39-41, приклади й пояснення структури) і функціональні означення
`get`/`prop`/`deflist`/`remprop` (ст.58-59). Усе перевірено напряму по
зображенню сторінки, не по OCR.

Це **не Appendix A**, і не Appendix B interpreter/PROG -- окрема тема
основного тіла маніфесту, згадана лише побіжно раніше
(`docs/S0-SEED-CONTRACT.md`'s пункт 4 про "ширшу мрію"). `PUTPROP` --
термін ІЗ ПІЗНІШИХ діалектів Lisp (MacLisp/Lisp 1.6) -- **не існує в
цьому маніфесті 1962 року** (перевірено: нуль збігів у повнотекстовому
пошуку). Реальна 1962-функція з тим самим призначенням -- `deflist`.

## Точні формули (ст.58-59)

```
prop[x;y;u] = [null[x] -> u[]; eq[car[x];y] -> cdr[x]; T -> prop[cdr[x];y;u]]
get[x;y]    = [null[x] -> NIL; eq[car[x];y] -> cadr[x]; T -> get[cdr[x];y]]  (as scanned -- see below)
deflist[x;ind]  -- список пар (u v), кожна пара додає ind/v на початок property list-у u
remprop[x;ind]  -- видаляє ВСІ входження ind (і його значення) зі списку x
```

## Реальна знахідка: неоднозначність у відсканованому зображенні, вирішена через внутрішню несуперечність

Рекурсивний крок `get` у відсканованому зображенні виглядає як
`get[cdr[x];y]` -- **але це не може бути правильним**. Property list
-- плаский, чергований список `(indicator1 value1 indicator2 value2
...)` (підтверджено власними діаграмами маніфесту для property list
`NIL` і `FF`, ст.39-40: `-1, APVAL, (ptr), PNAME, (ptr)` -- indicator
одразу за indicator-ом, значення між ними, без вкладених пар). Якщо
рекурсія `get` пропускала б лише ОДИН елемент (`cdr`, не `cddr`), то
наступний виклик порівнював би `y` проти ЗНАЧЕННЯ, а не indicator-а --
структурно неможливо для коректної роботи. Сусідня, споріднена формула
`prop[x;y;u] = [null[x]->u[]; eq[car[x];y]->cdr[x]; T->prop[cdr[x];y;u]]`
(та сама сторінка) **справді** використовує одинарний `cdr` -- і це
коректно для `prop`, бо `prop` -- загальніший, однокроковий пошук по
довільному списку (не по чергованих indicator/value парах). Це дало
крос-перевірку: `prop`'s власний одинарний `cdr` на тому самому
зображенні читається правильно, отже сканування зображення саме по
собі надійне -- розбіжність саме в `get`-рядку є або: (а) OCR/
роздільна здатність зображення дала "cdr" замість "cddr" (типовий
композитний accessor, який ця сама книга використовує повсюди --
`cadr`, `caddr`, `cadar`, `caddar`), або (б) реальна друкарська
помилка маніфесту. Обидва випадки мають те саме розв'язання.

**Реалізовано первісно**: `get[x;y] = [null[x]->NIL;
eq[car[x];y]->cadr[x]; T->get[cddr[x];y]]` -- позначено тоді як
**reconstruction-derived corrected reading**, не сліпа транскрипція.

## ВИПРАВЛЕНО 2026-09-22: попередня "корекція" сама була помилкою

Під час роботи над `flag`/`remflag` (нижче) з'ясувалось: **та сама
"корекція" вище -- помилкова**. Property list може містити **flag**
-- indicator без значення (ст.59: "an indicator on a property list
that does not have a property following it is called a flag"). Якщо
`get` пропускає по ДВА елементи (`cddr`) на кожному кроці, це working
ЛИШЕ якщо кожен запис -- строга пара (indicator value); flag ламає це
припущення (один елемент, не два), зсуваючи всі наступні порівняння.

**Одинарний `cdr`, як буквально відскановано, насправді правильний**:
`get` просто йде по одному елементу, шукаючи ПЕРШЕ входження `y`, і
повертає те, що йде відразу за ним (`cadr` у момент знаходження) --
це коректно працює однаково для чистих (indicator value) пар І для
списків, що змішують прапори (flags) з парами, незалежно від парності
позиції збігу. Крос-перевірка через сусідню формулу `prop` (яка також
використовує одинарний `cdr`) була правильною логікою -- висновок із
неї (що `get` МУСИТЬ відрізнятись) був передчасним і хибним.

**Виправлено**: `get[x;y] = [null[x]->NIL; eq[car[x];y]->cadr[x];
T->get[cdr[x];y]]` -- точно як відскановано, без "корекції". Усі 7
попередніх fixture (`01`-`07`) перевірено повторно -- усі проходять
без змін (жоден із них не змішував flags із парами, тому баг був
непомітний для них).

Це реальна, задокументована самокорекція методу, не просто виправлення
коду: висновок "зображення має бути неправильним" був зроблений без
достатньо ретельного обмірковування альтернативи (одинарний крок,
що коректно узагальнює й на flags) -- урок на майбутнє, чому
"структурна неможливість" варто перевіряти повторно, коли з'являється
новий, суміжний контекст (тут -- сама потреба реалізувати flags).

## Реалізація в `mccarthy-kernel.s`

Кожен символ отримує окремий, незалежний property list -- новий
`proplist_table`, index-паралельний до `symtab`, ініціалізований
`NIL_SYM` для кожного щойно інтернованого символу (у `intern`, не
заздалегідь -- `NIL_SYM`=1, не 0, тож заповнена нулями `.skip`-ділянка
сама по собі НЕ означає "порожньо"). Не моделюється "-1 sentinel
head" чи внутрішні indicator-и `PNAME`/`EXPR`/`SUBR`, якими реальна
система користується для власного зберігання функцій/імен -- це
704/CTSS-специфічна деталь представлення, яку цей kernel не поділяє
(функції тут живуть у `global_env` через `DEFINE`, не на property
list) -- реалізовано лише сам, загальний, user-visible механізм
`GET`/`DEFLIST`/`REMPROP`.

`GET`/`DEFLIST`/`REMPROP` -- звичайні примітиви з обчислюваними
аргументами (як `RPLACA`/`RPLACD`), не спеціальні форми: `x` в
кожному з них обчислюється до символу, точно за текстом маніфесту
("get[x;i]... x" -- атомарний символ, ст.40).

`DEFLIST` бере список пар `((u1 v1) (u2 v2) ...)` і для кожної пари
додає `ind`/`v` **на початок** property list-у `u` ("puts things on
at the front", ст.58) -- тож повторний `DEFLIST` з тим самим
indicator-ом НЕ фізично замінює старий запис, а екранує його (GET
завжди знаходить найновіший, найближчий до початку) -- саме так
маніфест описує "the old value will be replaced by the new one" як
СПОСТЕРЕЖУВАНИЙ ефект. Повертає список `u`-шок, узгоджено з
`define[x] = deflist[x;EXPR]` і "the value of define is the list of
u's" (ст.58) -- для істинності цієї рівності `deflist` сам мусить
повертати те саме).

`REMPROP` видаляє **всі** входження indicator-а (і значення, що йде
за ним) з property list-у символу, перебудовуючи відфільтрований
список, а не роблячи буквальний `RPLACD`-сплайс, як реальна система
(ст.59) -- той самий спостережуваний результат, простіше й безпечніше
в рукописному асемблері, не видима семантична різниця для викликача.

## `flag`/`remflag` (ст.59)

```
flag[l;ind]     -- кладе прапор ind (без значення) на початок property
                   list кожного символу зі списку l; "no property list
                   ever receives a duplicated flag" -- ідемпотентно.
remflag[l;ind]  -- видаляє ВСІ входження прапора ind (лише сам
                   indicator, БЕЗ "succeeding property", на відміну
                   від remprop -- у прапора немає значення, яке можна
                   було б помилково прихопити).
```

`REMPROP` і `REMFLAG` навмисно різні: `remprop_filter` видаляє два
елементи на збіг (indicator + значення), `remflag_filter` -- лише
один. Застосування НЕ ТОГО видалювача до прапора реально ламає
структуру (`REMPROP` на прапорі з'їсть наступний indicator, вважаючи
його "значенням" прапора) -- перевірено прямим (не закомiченим)
пробником під час розробки, не потрапило у fixture як таке.

## Fixtures

| Fixture | Що перевіряє |
|---|---|
| `01` | Базовий `DEFLIST` + `GET`, дві пари одночасно |
| `02` | Власне значення `DEFLIST` -- список `u`-шок |
| `03` | `GET` з indicator-ом, якого немає -- `NIL` |
| `04` | `GET` на символі, якого DEFLIST/PUTPROP ніколи не торкався -- `NIL` |
| `05` | Повторний `DEFLIST` тим самим indicator-ом екранує старе значення |
| `06` | `REMPROP` видаляє **обидва** (екрановане й старе) входження indicator-а |
| `07` | Один символ, кілька РІЗНИХ indicator-ів одночасно, не плутаються |
| `08` | `GET` коректно перестрибує через прапор, змішаний з реальною парою -- regression witness саме для виправлення `cddr`→`cdr` вище |
| `09` | Повторний `FLAG` тим самим indicator-ом не дублює запис |
| `10` | `REMFLAG` видаляє прапор, НЕ чіпаючи сусідню (indicator value) пару |

## Adversarial verification

`01`-`07` -- перевірено ще в PR #49 проти kernel до property lists
узагалі: 6 з 7 реально провалюються, `04` чесно не дискримінує (та
сама, вже задокументована причина). `08`-`10` (сьогоднішня робота) --
перевірено проти `HEAD` (тобто проти PR #49's версії, що вже мала
`GET`/`DEFLIST`/`REMPROP`, але з `cddr`-багом і без `FLAG`/`REMFLAG`
узагалі): `08` і `10` реально провалюються (`FLAG` незв'язаний -> `GET`
на indicator-і прапора дає `NIL` замість `COLOR`). `09` чесно НЕ
дискримінує проти `HEAD` -- `FLAG`'s відсутність там і коректна
"без дублювання" поведінка тут дають той самий видимий результат
(`NIL`) із протилежних причин; його реальна цінність -- пряма перевірка
власної, внутрішньої коректності нової реалізації (підтверджено прямим
запуском: зіпсована версія без idempotency-перевірки дала б `TRACE`
замість `NIL` на повторному `FLAG`), не порівняння зі старою версією.
